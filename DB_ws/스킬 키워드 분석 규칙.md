# 니케 스킬 설명문 분석 지침서
## 작성 이유
- 이 문서는 덱 빌더 시스템 구축을 위해 니케의 스킬 텍스트를 정형화하고 분석하여 db를 구축하기 위한 가이드라인 문서. 이 문서의 규칙을 따라 자동화되거나 수작업이 가능하도록 하기 위함.
- 주의 : 이 문서에서 사용되는 표현은 공식 표현이 아니며 스킬 키워드 db 구축의 편의를 위해 개발자가 임의로 만든 표현임.

## 개요
- 이 파이프라인은 니케의 스킬 설명문(원문)에서 게임적으로 의미 있는 표현(발동 시점·발동 조건·적용 대상·효과)만 추상화해 `skill_keyword_master_table`과 `nikke_keyword_link_table`을 채우는 것을 목표로 한다.
- DB에는 이 목적을 위한 테이블을 추가하지 않는다. 마스터 구축용 중간 산출물은 전부 엑셀(`nikke_skill_keyword.xlsx`)로 이원화하며, 엑셀은 매번 전체를 새로 생성한다("추가된 니케만 처리" 없음).
- 사람이 관리하는 입력은 세 가지다 — `공용 표현`, `효과 카테고리 분류표`, `키워드 통합`. 앞의 둘은 코드(`KoreanAnalyzer`) 안의 목록/사전이 원본이며, 엑셀 시트는 생성 시점에 그 원본으로 채워지는 결과물이다. `키워드 통합`의 원본은 db의 `skill_keyword_unify_table`이다("유사 표현 통합" 절 참고). 그 외 모든 산출물(`니케 스킬 설명`, `스킬 블록`, `고유 속성`, `전용 이름`, `스킬 키워드 디버깅 목록`, `제외 키워드`, `스킬 키워드 마스터`, `니케-키워드 링크`)은 100% 자동으로 재생성된다.
- 최종 마스터 키워드는 8열(발동 시점 / 발동 조건 / 적용 대상 / 효과 - 공격류 / 공격보조류 / 방어생존류 / 체력회복류 / 유틸리티류)이다. `선행 행동`은 분석 과정의 다섯 번째 분류로만 쓰이고 마스터에는 남지 않으며, `[고유 속성]`·`[스킬 1]`·`[스킬 2]`·`[버스트 스킬]`·`[특정 니케]` 토큰이 든 키워드도 마스터에서 제외한다 — 그런 표현은 대개 그 니케 전용이라 범용 필터로서 가치가 낮기 때문이다.

# DB 테이블들 설명
- nikke_info_table
    - 블라블라링크에서 크롤링한 니케 정보
- nikke_keyword_link_table
    - 니케와 스킬 키워드(발동 시점/발동 조건/적용 대상/효과)를 연결하는 테이블. gui에서 키워드 쿼리용.
    - nikke_info_table과 skill_keyword_master_table의 id를 연결
- skill_keyword_master_table
    - 스킬 키워드를 `발동 시점/발동 조건/적용 대상/효과 - 공격류/효과 - 공격보조류/효과 - 방어생존류/효과 - 체력회복류/효과 - 유틸리티류`로 분류한 테이블
    - 열마다 독립된 어휘라 `(category, keyword)` 쌍이 유일하다(같은 문자열이 다른 열에 있어도 됨). 앱도 키워드와 카테고리를 함께 조회한다
    - 이 문서와 ai의 작업이 이 테이블을 채우는 작업을 자동화 하기 위해 필수.
- skill_keyword_unify_table
    - 유사 표현 통합 결과. `category`(마스터 열 이름) / `original_keyword`(통합되어 마스터에서 빠지는 표현) / `unified_keyword`(마스터에 남는 대표 표현). (category, original_keyword)는 유일.
    - 승환님이 엑셀 '키워드 통합' 시트에서 수작업으로 확정한 내용을 13단계에서 반영하며, 이후 엑셀 재생성 때는 이 테이블이 '키워드 통합' 시트와 마스터 시트를 채운다("유사 표현 통합" 절 참고).
- (폐지) common_keyword_table, nikke_unique_mechanism_table, skill_keyword_mapping_table
    - 이 세 테이블은 db에 두지 않는다(2026-10-19 빈 테이블을 db에서 삭제하고 `createDBTable`의 정의도 제거). 대응하는 개념은 다음으로 대체됨
        - 공용 표현 : `KoreanAnalyzer` 코드 안의 목록으로 관리(사람이 100% 수동 관리, "공용 표현" 절 참고)
        - 니케 고유 메커니즘 : `고유 속성` 시트로 대체, 100% 자동 분석해 매번 새로 만듦(테이블로 유지하지 않음)
        - 유사 표현 통합 : `skill_keyword_unify_table`로 대체(위 항목). 통합이 없으면 마스터의 키워드는 디버깅 목록의 표현과 1:1

# DB 구축 순서
1. 크롤링을 해서 db의 nikke_info_table을 최신화
2. 스킬 설명들(Skill_1_description, Skill_2_description, Skill_bust_description)의 띄어쓰기 통일 및 결과를 엑셀 시트에 저장
    - '니케 스킬 설명' 시트 (니케 id 포함 — 이름이 같은 니케가 있음, 예 : 사쿠라)
    - 스킬 1, 스킬 2, 버스트 스킬의 띄어쓰기 통일한 결과 저장
    - 이후 진행되는 스킬 설명은 해당 시트의 스킬 설명으로 사용
    - 정규식 규칙만 사용하고 사전은 두지 않는다("띄어쓰기 통일 규칙" 절 참고)
3. 스킬 설명 구조 분해 및 결과를 엑셀 시트에 저장
    - '스킬 블록' 시트
    - `■` 단위로 블록을 나누고, 본문을 효과 / 부가 옵션 / 명칭으로 구분("본문 요소 판정 규칙" 절 참고)
    - 한 `■` 안에 헤더가 여러 개면 각 헤더를 독립된 블록으로 봄
4. 니케 고유 속성 분석 및 결과를 엑셀 시트에 저장
    - '고유 속성' 시트
    - 없는 니케는 None으로 저장
    - 있는 니케는 고유 속성 개수만큼 행(row) 사용
    - 100% 자동 분석이며 매번 새로 만드는 산출물("고유 속성" 절의 규칙을 그대로 적용)
5. 텍스트 치환
    1. `[고유 속성]` → `[스킬 1]`/`[스킬 2]`/`[버스트 스킬]` → `[특정 니케]`
    2. 하나의 통합 치환 패스로 처리(최장 일치 원칙, "치환 우선순위" 절 참고)
6. 5번의 결과인 니케 스킬 설명 텍스트를 '발동 시점', '발동 조건', '선행 행동', '적용 대상', '효과'로 분류
    - 해당 단계에서 효과를 상세하게 분류하는게 아니고 전체 맥락을 분류하는게 목적
    - '효과'를 제외한 나머지 분류는 문맥 안 어디든 존재할 수 있음을 주의
    - 분류 알고리즘은 "헤더 슬롯 분해" 절 참고
    - 선행 행동은 발동 시점/발동 조건을 정확히 분리하기 위한 중간 분류이며, 최종 스킬 키워드 마스터의 카테고리에는 포함되지 않는다("선행 행동" 절 참고)
7. 분류된 텍스트에서 숫자 치환
    - 분류된 목록에서 텍스트들의 숫자만 다르다면 해당 숫자부분만 n으로 치환
    - 분류된 목록에서 텍스트들의 숫자가 동일하다면 해당 숫자는 유지
    - 하나의 텍스트에서 여러 숫자가 등장할 때 각 숫자들이 모두 동일하지는 않을 수 있음
    - 판정은 항상 전체 데이터 기준(예외 화이트리스트 없음)
8. 7번의 결과에서 중복 제거 및 결과 엑셀 시트에 저장
    - '스킬 키워드 디버깅 목록' 시트
    - '발동 시점', '발동 조건', '선행 행동', '적용 대상', '효과'로 분류된 데이터 저장
9. 제외할 키워드 걸러내기
    - '제외 키워드' 시트
    - `[고유 속성]`/`[스킬 1]`/`[스킬 2]`/`[버스트 스킬]`/`[특정 니케]` 토큰이 든 키워드, 전용 이름(고유 속성은 아니지만 한 니케만 쓰는 이름)이 든 키워드, 그리고 선행 행동으로 분류된 키워드를 제외("토큰 키워드 제외" 절 참고)
    - 디버깅 목록 자체는 전체를 그대로 남기고, 제외된 키워드만 사유와 함께 별도 시트에 남김
10. 효과 카테고리 배정
    - 9번 결과의 효과 키워드 하나하나에 5개 카테고리 중 하나를 배정("효과 카테고리 배정" 절 참고)
11. 스킬 키워드 마스터 분류 완성
    - '스킬 키워드 마스터' 시트
    - '발동 시점', '발동 조건', '적용 대상', '효과 - 공격류', '효과 - 공격보조류', '효과 - 방어생존류', '효과 - 체력회복류', '효과 - 유틸리티류'로 분류
    - 열별 오름차순 독립 정렬. 통합(유사 표현을 하나로 묶는 것)은 사람이 수작업으로 하며("유사 표현 통합" 절), db의 통합 테이블이 비어 있으면(최초 구축) 8번의 결과가 그대로 마스터 키워드
    - 구현 : `buildUnifySheet`가 db 통합 테이블로 '키워드 통합' 시트(가로형)와 '통합 점검' 시트를 만들고, `buildMasterSheet`가 디버깅 목록에서 '제외 키워드' 시트에 오른 키워드(토큰/전용 이름/선행 행동)를 빼고 같은 열 안에서 통합을 적용해 적재한다. 효과는 10단계에서 배정한 카테고리 열로 나눈다. 미분류 효과가 하나라도 있으면 적재하지 않고 중단한다.
12. 니케-키워드 링크 생성
    - '니케-키워드 링크' 시트
    - '스킬 블록' 시트의 각 블록 키워드(발동 시점/발동 조건/적용 대상/효과)를 '키워드 통합' 시트로 번역한 뒤 마스터의 같은 열에서 찾아 (니케, 열, 키워드) 링크를 만든다. 키워드는 서로 독립이라 포함 관계로 링크를 퍼뜨리지 않는다("유사 표현 통합" 절 1번)
    - 시트 열: 니케 id / 니케 이름 / 열 / 키워드 / 출처 스킬. 키워드 id는 13단계에서 마스터를 db에 적재할 때 정해지므로 시트에는 키워드 문자열을 적는다. 같은 (니케, 열, 키워드)는 하나로 합친다
    - 번역 순서 : 통합 시트의 원래 표현이면 통합 표현으로(`[제외]`면 링크 없음) → 마스터에 있으면 그대로 → `제외 키워드` 시트에 있으면(토큰/전용 이름/선행 행동) 링크 없음 → 그 외는 오류로 중단
    - 시작 전에 `checkUnifyConsistency`("유사 표현 통합" 절의 일관성 점검)를 통과해야 한다
    - 구현 : `buildLinkSheet`
13. DB 반영
    - 마스터 시트 → skill_keyword_master_table, 링크 시트 → nikke_keyword_link_table, '키워드 통합' 시트 → skill_keyword_unify_table(세로형으로 변환)
    - 한 트랜잭션에서 세 테이블을 비우고 다시 적재
    - 구현 : `writeKeywordTablesToDb`. 마스터 키워드 id는 열 순서(발동 시점 → … → 효과 - 유틸리티류) + 열 안 시트 순서(오름차순)대로 1부터 매긴다(앱이 `ORDER BY category, id`로 버튼을 만들므로 열 안에서는 시트 순서가 곧 버튼 순서). 링크는 (니케 id, 키워드 id) 쌍으로 중복 없이 적재한다
    - 적재 전 검사(하나라도 걸리면 아무것도 쓰지 않음) : 통합 일관성 점검 통과, 링크 시트가 비어 있지 않음, 링크 키워드가 마스터 같은 열에 없음, 링크 니케 id가 `nikke_info_table`에 없음, 통합 시트 구조 오류
    - 같은 키워드 문자열이 다른 열에 있는 것은 허용한다 — 마스터 테이블의 유일 키는 `(category, keyword)`다(2026-10-19 변경, 예전 `keyword` 단독 UNIQUE인 db는 `createDBTable`이 키워드 id를 유지한 채 옮김)
    - 통합 테이블만 고칠 때는 `writeUnifyGroupsToDb`를 쓴다
14. 검증
    - '검증 결과' 시트(구분 / 항목 / 내용). 구현 : `validatePipeline` — 오류가 하나라도 있으면 실패
    - 오류 : 미분류 효과 / 링크 시트가 비었거나 마스터에 없는 키워드를 가리킴(링크 조회 실패) / 블록이 없는 스킬(스킬 1·스킬 2·버스트 스킬 각각 블록 1개 이상) / 링크가 하나도 없는 마스터 키워드 / 링크가 하나도 없는 니케 / 토큰(`[고유 속성]` 등)이 남은 마스터 키워드 / db(마스터·링크·통합 테이블)가 엑셀과 다름(13단계 미반영)
    - 경고(사람이 확인) : 숫자만 다른 마스터 키워드(숫자를 `n`으로 바꾸면 같은 열의 다른 키워드와 같아짐 — 통합 후보) / 니케 이름·스킬명이 그대로 남은 키워드(단어 단위로 맞추고 뒤에 붙은 조사는 허용 — `라이플`의 `라이`, `활성화`의 `성화` 같은 오탐 방지, 공용 표현은 제외) / '통합 점검' 시트 항목
    - 정보 : 값이 하나뿐이라 숫자가 남은 키워드. 7단계 규칙상 숫자는 전체 데이터에서 값이 하나뿐일 때만 남으므로 정상이며, 통합할 때 참고용으로만 남긴다
    - 2026-10-18 실행 결과 : 오류 0 / 경고 0 / 정보 105. 일부러 문제를 넣은 사본으로 각 검사가 실제로 잡는지 확인함

# 실행 방법
`DB_manager_nikke.py` 맨 아래 `if __name__ == '__main__':`의 **실행 설정** 플래그에서 실행할 작업만 `True`로 바꾼 뒤 파일을 실행한다(VSCode 실행 버튼).

| 플래그 | 단계 | 하는 일 |
|---|---|---|
| `RUN_CRAWLING` | 1 | 크롤링으로 `nikke_info_table` 최신화, 변경 보고서, 프로필 이미지 다운로드(기존 동작, 기본값 `True`) |
| `RUN_WORKBOOK` | 2~12 | DB 기준으로 `nikke_skill_keyword.xlsx` 전체 재생성(`KoreanAnalyzer.runWorkbookPipeline`). 반영 안 된 엑셀 수작업이 있으면 멈춤 |
| `FORCE_WORKBOOK` | — | `RUN_WORKBOOK`에서 반영 안 된 수작업이 있어도 엑셀을 새로 만듦(수작업은 사라짐) |
| `RUN_APPLY` | 12~14 | 사람이 고친 엑셀로 링크 재생성 → DB 반영 → 검증(`KoreanAnalyzer.runApplyPipeline`) |

- 일반적인 흐름 : `RUN_CRAWLING` → `RUN_WORKBOOK` → (엑셀에서 `통합 점검` 확인, `키워드 통합`·`스킬 키워드 마스터` 수정) → `RUN_APPLY`.
- 여러 플래그가 `True`면 crawl → workbook → apply 순서로 실행하고, 하나라도 실패하면 거기서 멈춘다.
- workbook/apply는 시작할 때 `DBManager.createDBTable`로 스킬 키워드 테이블(마스터/링크/통합)이 있는지 보장한다(이미 있으면 그대로). 이때 예전 정의의 테이블(마스터 `keyword` 단독 UNIQUE, 링크 외래키가 `nikke_info_table_legacy`를 가리킴)은 데이터를 유지한 채 고친다.
- 단계 실행 순서는 `KoreanAnalyzer.WORKBOOK_PIPELINE_STEPS` / `APPLY_PIPELINE_STEPS`에 있다.

## 변경 표시 (마지막 반영 대비)
`RUN_WORKBOOK`은 마지막 `RUN_APPLY` 이후 바뀐 곳을 색으로 칠하고 `변경 점검` 시트에 모은다(2026-10-21). 새 니케나 스킬 설명 변경이 키워드에 어떤 영향을 주는지 반영 전에 확인하는 용도다.
- **비교 기준 = `반영 기준` 시트** : `RUN_APPLY`가 13단계 직후(`saveAppliedBaseline`) 그 시점의 마스터 / 링크 / 스킬 설명을 남긴다. 니케는 id가 아니라 **(이름, 등급)** 으로 남긴다 — 크롤링이 니케 테이블을 다시 만들면서 id가 밀리기 때문. `RUN_WORKBOOK`은 덮어쓰기 전에 기존 엑셀의 이 시트를 읽어(`loadPreviousBaseline`) 새 엑셀에 그대로 넘긴다(`markWorkbookChanges`). 그래서 `RUN_WORKBOOK`을 여러 번 돌려도 기준은 다음 `RUN_APPLY` 전까지 유지된다. 엑셀 파일을 지우면 기준도 사라지고 그때는 색 없이 만들어진다(`변경 점검`에 `기준 없음`).
- **색** : 추가 = 초록(`C6EFCE`), 변경 = 노랑(`FFEB9C`), 삭제 = 빨강(`FFC7CE`, `변경 점검` 시트에서만)
    - `니케 스킬 설명` : 새 니케 행 초록, 설명이 바뀐 셀 노랑
    - `스킬 키워드 마스터` : 새로 생긴 키워드 셀 초록
    - `니케-키워드 링크` : 새로 생긴 링크 행 초록
- **`변경 점검` 시트**(구분 / 니케 이름 / 등급 / 열 / 내용) : `추가된 니케`, `사라진 니케`, `설명 변경(키워드 변화 있음)` / `설명 변경(키워드 변화 없음)`, `추가된 키워드`, `사라진 키워드`, `추가된 링크`, `사라진 링크`. 사라진 것은 새 엑셀에 행이 없어 색을 칠할 수 없으므로 이 시트에서만 보인다. 바뀐 것이 없으면 `변화 없음`.
- 최초 기준(2026-10-21)은 크롤링 직전 db 백업으로 만들어 넣었다(벨로타 : 펌킨 위치 추가, 길티 : 마이티 바니·신 : 스위프트 바니 설명 변경이 첫 표시 대상).
- 프로필 이미지 파일 이름은 `resource/<이름>_<등급>_profile.webp`이다(이름의 `:`는 `-`로 바꿈, 예: `resource/라피 - 레드 후드_SSR_profile.webp`). 이름이 같은 니케(사쿠라 SSR/SR)를 구분하려고 등급을 붙였다(2026-10-19). db의 `Path_img_profile`은 다음 크롤링 때 이 규칙으로 바뀐다.

# 유사 표현 통합
통합은 **사람(승환님)이 수작업**으로 하고, 결과는 db의 `skill_keyword_unify_table`에 저장한다. 이 절은 통합 시트를 어떻게 쓰는지, 무엇을 합치고 무엇을 합치지 않는지, 작업 순서와 점검 방법을 한곳에 모은 가이드다.

## 1. 통합이란 무엇이고 무엇이 아닌가
- 통합은 **"이 표현들은 필터에서 같은 키워드로 취급한다"는 번역표**다. `n회 공격 시`를 `공격 시`로 통합하면, 스킬 문구에 `n회 공격 시`라고 적힌 니케가 `공격 시` 키워드에 링크된다. 통합 표현이 마스터에 남고, 합쳐진 원래 표현은 마스터에서 빠진다.
- **키워드는 서로 독립이다(포함 관계 없음).** 앱은 선택한 키워드를 정확히 일치시켜 링크 테이블에서 찾는다. `전격 코드 적 전체에게`를 가진 니케는 `적 전체에게`에 링크되지 않는다. 한 키워드가 다른 키워드를 "포함"한다는 이유로 링크를 퍼뜨리지 않는다. 따라서 통합은 **같은 키워드로 봐도 되는 표현만** 묶어야 한다(아래 3절).
- 통합은 두 가지 일을 한다. ① 같은 뜻의 다른 표기를 하나로 합친다(동의어 통합). ② 필터에 의미 없는 정보(횟수, 수식어)를 뗀다(예: `n회 공격 시` → `공격 시`).
- 통합 행은 마스터에 키워드를 "살려 두는" 것이 아니라 **링크를 만드는 유일한 경로**다. 행을 지우면 그 표현을 쓰는 니케가 해당 키워드에 연결되지 않고, 어디에도 안 보내면 12단계가 오류로 멈춘다.

## 2. 통합 시트(`키워드 통합`) 작성법
### 2-1. 시트 구조(가로형)
| 열 | 통합 표현 | 비슷한 표현 1 | 비슷한 표현 2 | … |
|---|---|---|---|---|
| 적용 대상 | 자신에게 | 자기 자신에게 | 추가로 자신에게 | |
| 효과 - 유틸리티류 | [제외] | 스킬 1의 풀 차지 공격 횟수 조건이 … 로 변경 | | |

- **열**: 마스터 시트 열 이름 중 하나(`발동 시점` / `발동 조건` / `적용 대상` / `효과 - 공격류` / `효과 - 공격보조류` / `효과 - 방어생존류` / `효과 - 체력회복류` / `효과 - 유틸리티류`). 통합은 **같은 열 안에서만** 한다. 효과는 같은 카테고리 안에서만 합칠 수 있다.
- **통합 표현**: 마스터에 남을 키워드. 현재 키워드 목록에 있는 표현이어도 되고 승환님이 새로 쓴 문구여도 된다(예: `자신의 체력이 n% 이상일 때`는 목록에 없던 대표 문구).
- **비슷한 표현 1..N**: 이 행의 통합 표현으로 합쳐질 원래 표현들. 한 칸에 하나씩, 칸 개수는 자유(시트를 만들 때 최대 개수 + 3칸이 자동으로 준비됨).
- 한 행이 한 그룹이다. 같은 통합 표현을 두 행에 나눠 쓰지 말고 한 행에 모은다(두 행이어도 동작은 하지만 읽기 어렵다).
- 통합 표현을 비슷한 표현 칸에 다시 적어도 무시된다(무해). 같은 행 안의 중복 표현도 무시된다.

### 2-2. 원래 표현을 정확히 적는 법
- 원래 표현은 **현재 키워드 목록의 문자열 그대로**여야 한다. 숫자는 7단계 치환이 끝난 형태(`n`)로 적는다(예: `일반 공격 n회 공격 시`). 값이 하나뿐인 숫자는 치환되지 않고 그대로 있으므로 목록에 보이는 대로 적는다(예: `대상 파츠 5회 명중 시`, `방어력 8.15%`).
- 어떤 표현이 목록에 있는지는 `스킬 키워드 디버깅 목록` 시트(제외된 것은 `제외 키워드` 시트)에서 확인한다. 통합 표현으로 쓸 문구가 이미 마스터에 있는지는 `스킬 키워드 마스터` 시트에서 본다.
- 오타가 나면 그 행은 효과가 없고 `통합 점검` 시트에 `낡은 원래 표현`으로 뜬다.

### 2-3. 특수 표기 `[제외]`
- **통합 표현 칸에 `[제외]`를 쓰면** 그 행의 원래 표현들은 어디에도 통합하지 않고 마스터에서 뺀다. 링크도 만들지 않는다(그 표현으로는 니케를 찾을 수 없게 됨).
- 쓰는 때: 검색에 쓸 필요가 없는 키워드, 뜻이 모호한 키워드, 단 한 니케에만 쓰이는 매우 특수한 키워드.
- 한 열에 `[제외]` 행은 하나만 두고 그 안에 모은다.
- 대체할 키워드가 있으면 `[제외]`가 아니라 **대체(통합)** 로 쓴다. `[제외]`는 그 표현을 가진 니케가 그 키워드로는 아예 안 잡히게 하는 선택이다.

## 3. 무엇을 합치고 무엇을 합치지 않는가
기준 한 줄: **"이 두 표현을 서로 다른 버튼으로 두면 필터 목적에서 정보가 달라지는가?"** 달라지지 않으면 합친다.

### 합쳐도 되는 것(승환님 결정 사례)
| 유형 | 예 | 이유 |
|---|---|---|
| 횟수/개수 제거 | `n회 공격 시`, `n회 피격 시`, `n회 사격 시` → `공격 시`, `피격 시`, `사격 시` / `일반 공격 n회 공격 시` → `일반 공격 시` / `대상 파츠 5회 명중 시` → `대상 파츠 명중 시` / `n회 순차 공격` → `순차 공격` | 몇 회인지는 필터에서 중요하지 않다 |
| 의미 없는 수식어 | `추가로 아군 전체에게` → `아군 전체에게`, `추가로 자신에게` → `자신에게`, `추가로 적 1기에게` → `적 1기에게`(새 키워드 — 처음엔 `적 전체에게`로 합쳤다가 대상 범위가 달라 되돌림) | 맨 앞 수식어는 필터에 의미가 없다 |
| 공용 용어의 동의어 | `랩쳐 등장 시` → `적 등장 시`, `랩쳐 사망 시` → `적 사망 시` | `랩쳐`는 게임에서 적을 부르는 공용 표현이다 |
| 조건 어미 | `~일 때 한하여` / `~라면` / `~일 때` → 하나 | 같은 조건의 다른 어미. `한하여`도 쓸모없는 표현으로 정했다 |
| 표기 차이 | `자기 자신에게` → `자신에게`, `조준선에서 가장 가까운` → `조준선에 가장 가까운`, `돌입 시` → `진입 시`, `변경` → `적용`, `시전자 최종 최대 체력` → `시전자의 최종 최대 체력` | 같은 뜻의 표기 차이 |
| 단위/형식 차이 | `탄환 충전 n%` / `탄환 충전 n발` → `탄환 충전`, `해로운 효과 면역 1개`/`∞개` → `해로운 효과 면역`, `적 전체 도발`/`적 전체를 도발` → `도발` | 단위나 범위 표기는 필터에서 중요하지 않다 |
| 단독 숫자 표기 | `방어력 8.15%` → `방어력 n% ▲` | 값이 하나뿐이라 치환되지 않았을 뿐 같은 표현 |
| 긴 설명문 → 이름 | 도로시의 긴 낙인 설명문 → `낙인` | 설명이 너무 길고 `낙인`이 공용 표현이라 이름이 직관적 |
| CC기 | `기절 면역` → `기절` | CC기는 필터에서 중요하지 않다(키워드 존재 여부만 중요, 공격류가 중요) — 승환님 기준 |

### 합치지 않는 것(또는 신중히 볼 것)
- **대상을 구분하는 정보가 다른 표현**: `전격 코드 적 전체에게`, `풍압 코드 적 전체에게`, `코어가 활성화된 적 전체에게`는 각각 별개 키워드이며 `적 전체에게`로 합치지 않는다(필터에서 서로 걸리지 않게 하려는 설계). 같은 수식(`전격 코드`)을 공유하는 표기 차이(`전격 코드 적에게` → `전격 코드 적 전체에게`)만 합친다.
- **열이 다른 표현**은 합치지 않는다(시점끼리, 조건끼리, 대상끼리, 같은 효과 카테고리끼리만).
- **의미가 달라 보이는 병합은 그 병합이 실제로 검색 결과를 바꾸는지 확인한다.** 원문 문맥과, 그 표현을 쓰는 니케가 대표 키워드를 이미 다른 블록에 갖고 있는지를 본다. 2026-10-18 확인 결과:
    - 유지(검색 영향 없음 또는 무의미): `자신의 체력이 80% 미만이라면` → `n% 이하일 때`(앨리스, 미만/이하 차이는 필터에서 무의미), `니케를 제외한 적이 1기 일 때` → `n기 이상일 때`(트리나 — 같은 버스트에 `2기 이상일 때` 블록이 있어 어차피 대표에 연결), `방어형 아군 2기에게` → `방어형 아군 전체에게`(키리 — 버스트에 `방어형 아군 전체에게`가 따로 있음), `전격 코드 적에게` → `전격 코드 적 전체에게`(원문이 원래 전체 대상), `무작위 적 n기에게` → `무작위 적들에게`(둘 다 무작위 대상).
    - 되돌림(검색 결과가 틀어짐): `추가로 적 1기에게` → `적 전체에게`는 원래 `적 전체에게` 블록이 없는 노벨을 `적 전체에게` 필터에 넣었으므로 새 키워드 `적 1기에게`로 바꿨다.

## 4. 대체와 제외, 그리고 연쇄 금지
- 지운 표현이 "다른 키워드로 대체 가능"하면 그 키워드 행에 **비슷한 표현으로 추가**한다(니케가 대체 키워드로 링크됨). 대체할 곳이 없고 검색이 필요 없으면 `[제외]`.
- 마스터 시트에서 키워드를 손으로 지우기만 하고 통합 시트에 흔적을 안 남기면, 12단계가 "마스터에도 통합 시트에도 없는 키워드"로 멈춘다. 항상 통합 시트에 행(대체 또는 `[제외]`)으로 남긴다.
- **연쇄 금지**: 원래 표현이 다른 그룹의 통합 표현이어서는 안 된다(`A → B`, `B → C` 금지). 처음부터 `A → C`, `B → C`로 직접 쓴다. 현재 키워드 목록에 없는 낡은 표현을 중간 다리로 삼을 수도 없다.
- 한 원래 표현은 하나의 그룹에만 속한다.

## 5. 작업 순서
실행은 `DB_manager_nikke.py`의 실행 설정 플래그로 한다("실행 방법" 절).
1. `RUN_WORKBOOK = True`로 실행해 엑셀을 DB에서 새로 만든다. `키워드 통합` 시트에는 DB의 기존 통합이 들어 있고, `통합 점검` 시트에 낡은 표현/신규 표현이 나온다.
2. `통합 점검`의 `신규 표현`(이전에 반영된 마스터에 없던 키워드)을 보고 통합할지 정한다. `낡은 원래 표현`은 목록에서 사라진 표현이라 지우거나 고친다.
3. `키워드 통합` 시트에 행을 추가/수정한다.
4. 마스터 시트는 **통합 시트와 일치하게** 맞춘다 — 원래 표현은 마스터에서 지우고, 새 통합 표현은 마스터에 남긴다.
   - 엑셀의 마스터 시트는 재생성 때 "현재 키워드 + 통합 시트"로 다시 계산된다(DB 마스터 테이블을 그대로 읽어 오지 않음). 그래서 마스터에 손으로 추가한 표현(현재 키워드도 통합 표현도 아닌 것)은 재생성 때 사라진다 — 마스터에 남기고 싶은 표현은 반드시 통합 시트의 통합 표현으로 적는다. 일관성 점검이 이런 표현을 경고로 알려 준다.
5. `RUN_APPLY = True`로 실행해 반영한다. 일관성 점검(`checkUnifyConsistency`) → 12단계 링크 재생성 → 13단계 DB 반영(마스터·링크·통합을 한 트랜잭션) → 14단계 검증 순서로 돌고, 하나라도 실패하면 그 자리에서 멈춘다(DB는 바뀌지 않음). 결과는 `검증 결과` 시트에 남는다.
6. **DB에 반영하기 전에 엑셀을 다시 만들면 수작업이 사라진다.** 엑셀은 항상 DB가 원본이다. 그래서 `RUN_WORKBOOK`은 기존 엑셀에 반영 안 된 수작업(통합 시트가 DB와 다르거나, 마스터 시트가 계산 결과와 다름)이 있으면 엑셀을 덮어쓰지 않고 멈춘다. 수작업을 버려도 될 때만 `FORCE_WORKBOOK = True`로 실행한다.
7. 필요하면 `RUN_WORKBOOK`으로 다시 만들어 마스터와 링크가 의도대로 나오는지 확인한다(반영이 끝났으므로 멈추지 않는다).

## 6. 점검 시트와 일관성 점검 읽는 법
- **`통합 점검` 시트(경고, 중단 아님)**: `낡은 원래 표현`(현재 목록에 없음 — 오타이거나 규칙을 고쳐 문자열이 바뀜), `카테고리 불일치`(효과가 다른 카테고리로 옮겨 가 통합이 적용되지 않음), `그룹 전체가 낡음`(원래 표현도 통합 표현도 목록에 없음), `신규 표현`(이전에 DB에 반영된 마스터/통합에 없던 표현 — DB 마스터가 있을 때만 표시).
- **일관성 점검 오류(`checkUnifyConsistency`, 하나라도 있으면 실패)**: ① 통합 시트로 옮긴 원래 표현이 마스터의 같은 열에 남아 있음 ② 통합 표현이 마스터에 없음(`[제외]` 제외) ③ 현재 키워드가 마스터에도 통합 시트의 원래 표현에도 없음(링크할 곳이 없음) ④ 구조 오류 — 같은 원래 표현이 두 그룹에 있음 / 연쇄 / 자기 자신으로 통합 / 열 이름 오류.
- 경고: 마스터에만 있고 현재 키워드도 통합 표현도 아닌 표현.

## 7. 12단계 링크와의 관계
- 링크는 "블록의 키워드 → 통합 시트로 번역 → 마스터의 같은 열에서 조회" 순서로 만들어진다(`buildLinkSheet`). 번역 후 통합 표현이 `[제외]`이거나 `제외 키워드`(토큰/전용 이름/선행 행동)에 있는 표현은 링크가 생기지 않는다. 마스터·통합 시트·제외 키워드 어디에도 없는 표현이 하나라도 있으면 시트를 쓰지 않고 중단한다.
- 새 니케가 추가되어 새 표현이 생기면 `통합 점검`의 `신규 표현`으로 뜬다. 합칠 것은 통합 행으로 쓰고, 그대로 두면 그 표현이 새 마스터 키워드가 된다.
- 숫자는 7단계 `n` 치환이 끝난 표현을 기준으로 통합한다.

# 스킬 설명 추상화 및 분류 체계
## 추상화 토큰
스킬 설명에 기재된 텍스트 중 가변적이거나 명사 계열의 인자들은 아래와 같이 표준 대괄호 토큰으로 치환하여 관리
* `[스킬 1]` : 스킬 1 이름
* `[스킬 2]` : 스킬 2 이름
* `[버스트 스킬]` : 버스트 스킬 이름
* `[특정 니케]` : '나의 왕', '나의 우상'
* `[고유 속성]` : 니케의 고유한 스킬 효과 이름

## 스킬 설명 분류 표현 (8대 표준 카테고리)
스킬 텍스트는 분석 과정에서 먼저 `발동 시점 / 발동 조건 / 선행 행동 / 적용 대상 / 효과` 다섯 갈래로 나뉜다. 이 중 `선행 행동`은 최종 분류가 아니라 발동 시점·발동 조건을 정확히 분리하기 위한 중간 분류이며(자세한 내용은 "선행 행동" 절 참고), 최종적으로는 아래 8대 표준 카테고리로만 파싱되어 오름차순으로 독립 정렬 적재된다.
* `[발동 시점]` : 해당 효과가 발동하는 시점 (예: `n초마다`, `피격 시`, `전투 시작 시`, `풀 버스트 타임 진입 시`)
* `[발동 조건]` : 해당 효과가 발동할 수 있는 조건 (예: `자신의 체력이 n% 이상일 때`, `동일 스쿼드 아군이 있다면`)
* `[적용 대상]` : 해당 효과를 적용할 대상 (예: `아군 전체에게`, `공격력 가장 높은 적 n기에게`, `[고유 속성] 상태인 대상에게`)
* `[효과]` : 실질적인 스킬의 효과 (아래 5대 카테고리로 상세 분류)
    * `[효과 - 공격류]` : 대미지 및 공격 관련 효과 (예: `최종 공격력 n% 대미지`, `공격력 n% ▲`, `우월 코드 공격 대미지 n% ▲`, `관통 특화`)
    * `[효과 - 공격보조류]` : 공격을 보조하거나 재장전, 장탄 수 등을 지원하는 효과 (예: `최대 장탄 수 n% ▲`, `재장전 속도 n% ▲`, `버스트 게이지 충전 속도 n% ▲`, `사용 무기 변경`)
    * `[효과 - 방어생존류]` : 방어력, 보호막, 무적, 불굴, 도발 등 생존에 특화된 효과 (예: `방어력 n% ▲`, `시전자의 최종 최대 체력 비례 n% 보호막`, `도발`, `불굴`, `무적`)
    * `[효과 - 체력회복류]` : 체력, 엄폐물 체력 등을 회복시키는 효과 (예: `시전자의 최종 최대 체력 비례 n% 회복`, `체력 회복량 n% ▲`, `엄폐물 체력 회복 n%`)
    * `[효과 - 유틸리티류]` : 버스트 재사용 시간 제어, 이로운/해로운 효과 제어 등 전술 효과 (예: `버스트 스킬 재사용 시간 n초 ▼`, `해로운 효과 면역`, `이로운 효과 해제`, `기절`)
* 최종 분류 : 발동 시점 / 발동 조건 / 적용 대상 / 효과 - 공격류 / 효과 - 공격보조류 / 효과 - 방어생존류 / 효과 - 체력회복류 / 효과 - 유틸리티류 (총 8열)

## 선행 행동
* 정의 : 효과가 실제로 나가기 전에 스킬이 수행하는 동작. 헤더(또는 서브 헤더)에서 `~후`로 끝나는 절이 여기 해당한다.
* 판별 규칙 : 헤더(또는 서브 헤더)에서 `~후`로 끝나는 절은 예외 없이 선행 행동으로 뗀다. 발동 시점처럼 보이는 경우(예: 은화의 `마지막 탄환 공격 후`)를 위한 예외를 따로 두지 않고 일괄 처리한다.
* 분해 절차 : `~후`로 끝나는 절을 헤더에서 추출해 선행 행동으로 두고, 남은 텍스트에는 "헤더 슬롯 분해" 규칙을 그대로 적용한다. `~후` 절이 문장 중간에 있어도 그 부분만 빼고 앞뒤를 이어 붙인 뒤 분해한다.
* 예시

    | 원문 | 선행 행동 | 남은 텍스트 → 분해 결과 |
    |---|---|---|
    | 디젤 : `자신이 [고유 속성] 최대 중첩 상태라면 중첩 해제 후 아군 전체에게` | 중첩 해제 후 | `자신이 [고유 속성] 최대 중첩 상태라면 아군 전체에게` → 발동 조건 + 적용 대상 |
    | 은화 : `마지막 탄환 공격 후 자신에게` | 마지막 탄환 공격 후 | `자신에게` → 적용 대상만(시점 없음) |
    | 메이든 : 아이스 로즈 : `MP 사용 후 자신에게` | MP 사용 후 | `자신에게` → 적용 대상만(시점 없음) |
    | 라플라스 : 얼티밋 히어로 : `자신이 오버 에너지 100% 도달 시 초기화 후 자신에게` | 초기화 후 | `자신이 오버 에너지 100% 도달 시 자신에게` → 발동 시점 + 적용 대상 |
    | 그레이브 : `미래 예지 상태 적용 후 일반 공격 명중 시 자신에게` | 미래 예지 상태 적용 후 | `일반 공격 명중 시 자신에게` → 발동 시점 + 적용 대상 |

* 최종 마스터에는 열로 남지 않는다. 선행 행동으로 분류된 키워드는 "토큰 키워드 제외" 단계에서 제외된다.

## 치환 우선순위 (최장 일치)
* 니케마다 치환 후보 풀을 하나로 모은다 = 전역 고유 속성 전체(다른 니케 것도 포함 — 규칙 4 때문) + 이 니케의 스킬명 3개(스킬 1/2/버스트) + `나의 왕`/`나의 우상`.
* 텍스트를 왼쪽부터 훑으며, 그 위치에서 시작하는 후보 중 **가장 긴 것**을 골라 치환한다(렉서의 "최장 일치" 원칙과 동일). 길이가 같으면 `[고유 속성]` → `[스킬]` → `[특정 니케]` 순으로 고른다.
* `[고유 속성]`/`[스킬 1·2·버스트 스킬]`/`[특정 니케]` 치환은 순서대로 실행하는 별개 단계가 아니라, 위 후보 풀을 한 번에 놓고 처리하는 하나의 통합 치환 패스로 구현해야 한다. 순차로 실행하면 먼저 실행된 단계가 더 짧은 후보를 앞서 매칭해버려 긴 후보가 깨질 수 있다.
* 동점 시 `[고유 속성]`이 이기는 근거는 임의 결정이 아니라 규칙 2(스킬 이름 연계)의 취지 그 자체다 — 규칙 2가 드는 예시(스킬 이름과 동일한 이름도 고유 속성으로 인정)가 정확히 이 동점 상황이다.
* 검증 예시

    | 사례 | 겹치는 후보 | 결과 |
    |---|---|---|
    | 델타 : 닌자 시프 | 스킬명 `인법 카모플라쥬`(8자) vs 은화의 고유 속성 `카모플라쥬`(5자) | 더 긴 `인법 카모플라쥬`가 통째로 `[스킬 2]`. 순서대로 실행했다면 `카모플라쥬`가 먼저 매칭돼 `인법 [고유 속성]`으로 깨졌을 것 |
    | 백학 | 고유 속성 `회복 독점 서약`(7자) vs 스킬명 `독점 서약`(4자) | 고유 속성이 원래 더 길어 자연히 `[고유 속성]`. 동점 규칙까지 갈 필요 없음 |
    | 아스카 : WILLE | 고유 속성 `섬멸 태세`와 `섬멸` | `섬멸 태세`를 먼저 통째로 치환, 남는 `섬멸`은 따로 `[고유 속성]` |
    | 일레그 | 버스트 스킬명 `붐 인스톨` == 고유 속성 `붐 인스톨`(완전 동일 문자열) | 길이 동점 → `[고유 속성]` 승리 |
    | 율리아 | 스킬명 `크레센도`(다른 스킬의 이름) == 고유 속성 `크레센도`, 스킬명 `데크레센도`가 이를 포함 | `데크레센도`는 더 길어 그대로 `[스킬 X]`. 독립된 `크레센도`는 스킬명과 길이가 같아 동점 → `[고유 속성]` 승리 |

* 단어 경계 등 오치환 대책은 이번 범위에서 두지 않는다.

## 헤더 슬롯 분해 (종류 기반)
* "앞이 시점, 뒤가 조건"이라는 위치 가정을 쓰지 않는다. 조건이 시점보다 먼저 오는 니케가 있을 수 있기 때문에, 순서가 아니라 조각의 종류로 판단한다.
* 적용 대상(`~에게`로 끝나는 부분)을 뗀 나머지 텍스트를 경계 어미가 나올 때마다 조각으로 자르고, 각 조각을 종류로 분류한다.
    1. 어미가 `시/후/마다/중`이고 바로 뒤에 `한하여`가 안 붙으면 → 시점형
    2. 어미가 `라면/다면/경우/확률로/이면/으면/했다면`이거나, `때/라면` 등이 `한하여`로 바로 이어지면(그 덩어리를 하나의 어미로 봄) → 조건형. `한하여`/`마다`가 따라붙지 않는 단독 `때`(`~이하일 때`, `~적용될 때`, `~배치됐을 때`)도 조건형 어미다(`자신의 체력이 20% 이하일 때 자신에게` → 조건 `자신의 체력이 20% 이하일 때` + 대상 `자신에게`)
    3. 바로 붙어 있는 같은 종류의 조각은 하나로 합친다. 단 발동 시점이 `A 시와 B 시`로 이어진 경우(예: `전투 시작 시와 풀 버스트 타임 종료 시`)는 시점 두 개이므로 `A 시`/`B 시`로 쪼갠다(2026-10-16 변경 — 아래 "복합 시점 분리" 참고)
    4. 시점형 조각들은 발동 시점에, 조건형 조각들은 발동 조건에 넣는다. 순서는 결과에 영향을 주지 않는다.
* `~후`로 끝나는 선행 행동은 이 분해보다 먼저 처리한다("선행 행동" 절 참고).
* 검증 예시

    | 원문 | 조각 분해 | 결과 |
    |---|---|---|
    | 아니스 : 스타(정순) `전투 시작 시 자신이 생존 상태일 때 한하여 아군 전체에게` | [전투 시작 시]시점 + [자신이 생존 상태일 때 한하여]조건 | 시점=`전투 시작 시`, 조건=`자신이 생존 상태일 때 한하여` |
    | 스노우 화이트 : 헤비암즈(역순) `세븐스 드워프 풀 액티브 상태일 때 한하여 풀 차지 시 자신에게` | [~상태일 때 한하여]조건 + [풀 차지 시]시점 | 조건=`~상태일 때 한하여`, 시점=`풀 차지 시` |
    | 템프테이션(조건만) `자신의 체력이 90% 이상일 때 한하여 아군 전체에게` | [~이상일 때 한하여]조건 하나뿐 | 조건=`자신의 체력이 90% 이상일 때 한하여`, 시점 없음 |
    | 라피 : 레드 후드(복합 시점) `전투 시작 시와 풀 버스트 타임 종료 시` | 한 절(경계 어미 뒤에 `와`가 바로 붙어 안 쪼개짐) | 시점=`전투 시작 시` + `풀 버스트 타임 종료 시`(두 값, 아래 "복합 시점 분리") |
    | 조건+시점 혼합 `자신이 구경났냐 짜식들아!! 상태일 때 한하여 2초 마다 적 전체에게` | [~상태일 때 한하여]조건 + [2초 마다]시점 | 조건=`~상태일 때 한하여`, 시점=`2초 마다` |

* `확률로`는 항상 자기 앞에 진짜 시점이 따로 있으므로(`피격 시 n% 확률로` 등) 같은 문제가 없다.
* 경계 어미는 "단어의 끝 글자"가 아니라 어미여야 한다. `명중`의 끝 글자 `중`, `무시`/`임시`의 끝 글자 `시`는 어미로 보지 않는다(`대상 : 명중 대상에게`가 발동 시점 `대상 : 명중` + 대상 `대상에게`로 갈라지거나, `방어력 무시 대미지로 적용`이 시점 `…방어력 무시`로 갈라지던 오류의 원인). `명중 시`처럼 뒤에 `시`가 따로 붙는 경우는 `시`가 어미라 영향이 없다. 이런 단어가 새로 발견되면 이 예외 목록에 추가한다. `아군 중`/`적 중`의 `중`은 "~ 가운데"라는 범위 표현이라 어미가 아니다(`0.2초마다 록 온 상태가 아닌 적 중 조준선에 가장 가까운 대상에게`는 시점 `0.2초마다` + 대상 `록 온 상태가 아닌 적 중 조준선에 가장 가까운 대상에게`, `아군 중 자신을 제외한 방어형 아군이 없다면`은 통째로 조건).
* 어미 없이 이어지는 수식 덩어리(`직전에 버스트 스킬을 사용한 기본 버스트 단계가 Step 3인 아군 전체에게`)는 더 쪼개지 않고 한 덩어리 대상으로 유지한다(승환님 결정).

## 복합 시점 분리 (`A 시와 B 시`)
- 발동 시점 절이 정규식 `^(.+?시)와 (.+시)$`에 맞으면 `A 시`, `B 시` 두 시점으로 쪼개 한 블록의 '발동 시점' 칸에 줄바꿈(`
`)으로 이어 저장한다. 7단계(숫자 치환)는 시점 값 하나하나를 따로 치환하고, 8단계(디버깅 목록)도 값마다 따로 적재한다. 12단계 링크는 두 시점 모두에 연결한다.
- **주어 물려받기** : 뒤 절에서 `시`를 뺀 부분이 한 단어뿐이면(`랩쳐 등장 시와 사망 시`의 `사망 시`) 앞 절의 주어를 공유한다는 뜻이므로, 앞 절에서 마지막 `<동사> 시`를 뺀 앞부분(주어)을 붙여 쪼갠다 → `랩쳐 등장 시` + `랩쳐 사망 시`(2026-10-18 승환님 결정). 물려받을 주어가 없으면 쪼개지 않는다.
- **적용 범위** : 발동 시점만. 발동 조건/적용 대상의 `와/과`(`자신과 양 옆에 있는 아군 2기에게`, `대상과 주변의 적 2기에게`, `[고유 속성]와 [고유 속성] 상태일 때`)는 명사 나열이라 쪼개지 않는다. 효과 문구에는 진짜 `와/과` 연결이 없다(2026-10-16 조사).
- 효과 : `전투 시작 시와 …` 6종이 사라지고 `전투 시작 시`/`버스트 스킬 사용 시`/`풀 버스트 타임 종료 시`/`최대 장탄 재장전 완료 시`/`풀 차지 상태를 n초 이상 유지 시`/`버스트 n단계 진입 시`는 이미 있던 키워드에 합쳐진다(새 키워드 없음). 토큰 때문에 통째로 제외되던 `전투 시작 시와 [고유 속성] 해제 시`는 `전투 시작 시`만 살아난다.

## 공용 표현
* 고유 속성은 아니지만 `승리의 여신 : 니케`에서 통용되는 표현으로 고유 속성 필터링 및 스킬 키워드 필터링을 위한 일반 표현을 말함.
* 필터링해서 없애거나 공용 표현 자체로 스킬 키워드로 만들기 위함.
* 원본은 `KoreanAnalyzer` 코드 안의 목록이며, 100% 사람이 수작업으로 관리한다. `공용 표현` 시트는 엑셀을 생성하는 시점에 이 목록으로 채워지는 결과물일 뿐이다 — 수정은 반드시 코드의 목록에서 하고, 엑셀 시트를 직접 고치지 않는다.
* 예시) 도발, 주목, 불굴, 사용 무기 변경, 디코이, 타겟, 낙인 등
* 고유 속성 규칙 8(헤더 틀 후보)을 돌려 보고 일반 명사가 후보로 걸려 나오면(예: `체력`, `스킬`, `버스트`) 이 목록에 추가한다. 이런 단어가 고유 속성이 되면 5단계 치환이 `풀 버스트 타임` → `풀 [고유 속성] 타임`처럼 전체 텍스트를 망가뜨리므로, 새 후보가 나올 때마다 고유 속성 시트를 눈으로 확인한다.

## 고유 속성
* 고유 속성이란
    - 해당 니케의 스킬1, 스킬2, 버스트스킬 설명에 `효과`로 분류되는 명사형 표현이 해당 니케 혹은 다른 니케의 `발동 시점/발동 조건/적용 대상`에 등장하는 표현
    - 고유 속성은 여러 니케가 가질 수 있음. '무대 파트 : 보컬'=>'민트, 프리카', '1more'=>'퀸(마코토),유키코'등.
    - "언급"은 위치(헤더 줄인지, `[효과]`로 분류되는 문구인지)가 아니라 표현의 종류(발동 시점/발동 조건/적용 대상 성격을 가졌는가)를 기준으로 판단한다. 그런 성격의 표현은 헤더 줄뿐 아니라 `[효과]`로 분류되는 문구 안에도 있을 수 있다 — 규칙 6은 규칙 1의 예외가 아니라 이 점을 알려주는 규칙이다.
    - `X를 Y로 변경` 형태의 효과 문구(트리나 `뻗은 뿌리를 시든 뿌리로 변경`)는 X(변경 대상)와 Y(변경 결과)가 모두 적용 대상 성격의 표현이라 "언급"으로 본다. 그래서 `뻗은 뿌리`, `시든 뿌리`가 각각 트리나의 고유 속성이 된다. (`X 해제`/`X 삭제` 같은 단순 동작 문구는 언급이 아니다 — 디스트로이, 핀 포인트처럼 헤더에 한 번도 안 나오는 이름은 고유 속성이 아니다.)
    - `나의 왕`, `나의 우상`은 고유 속성이 아니다. `[효과]`로 부여되는 이름이 아니라 특정 니케를 가리키는 호칭이므로 정의와 규칙 3(시전 주체)에 이미 맞지 않는다(별도 예외 규칙 불필요). 이 두 표현은 `[특정 니케]` 토큰으로 별도 처리한다(추상화 토큰 참고).
* 고유 속성을 분석하는 이유
    - 스킬 키워드를 추상화해서 개수를 줄이기 위해서 니케들의 스킬 설명문의 고유 매커니즘 이름을 '고유 속성'으로 정할 필요가 있음
* 고유 속성 분석 규칙
    1. **조건부/대상부 언급 필수**
        * 만약 `발동 시점/발동 조건/적용 대상`에서 단 한 번도 언급되지 않는 명사는 고유 속성으로 분류하지 않음.
    2. **스킬 이름 연계**
        * 스킬 이름과 동일한 이름이 표현에 등장하면서 다른 스킬 설명 문구에 포함되는 표현도 인정.
        * 예시) `일레그`의 `[붐 인스톨]` -> 버스트 스킬 이름
        * 예시) `아스카 : WILLE`의 `[안티 AT 필드]` -> 스킬1 이름
    3. **시전(생산) 주체**
        * 해당 니케가 스스로 `[효과]`로 분류되는 문구를 통해 그 기믹/상태를 부여/획득/생성해야 함.
        * 단지 타 니케의 기믹을 조건문으로 대조하거나 해제/삭제만 해주는 니케는 시전자가 아니므로 소유권이 없음.
        * 예시) `민트`와 `프리카`의 `무대파트 : 보컬` -> `민트`의 버스트 스킬, `프리카`의 스킬2.
        * 예시) `퀸(마코토)`와 `유키코`의 `1more` -> `퀸(마코토)`의 버스트 스킬, `유키코`의 버스트 스킬
    4. **타 니케 설명문 내 등장 가능**
        * 고유 속성은 다른 니케의 스킬 설명 문구(해제/삭제/조건 대조 등)에 포함될 수 있습니다. 이때, 해당 속성의 실제 소유권은 **시전하는 니케**가 보유.
        * 예시) `민트`의 `떼창` -> `프리카`의 스킬2 등장
        * 예시) `은화 : 텍티컬 업`의 `내부 폭발탄` -> `베스티 : 텍티컬 업`의 스킬2 등장
        * 예시) `엠마 : 텍티컬 업`의 `전장 조성` -> `베스티 : 텍티컬 업`의 스킬2 등장
        * 예시) `유키코`의 `추격` -> `퀸(마코토)`의 스킬1 등장
    5. **공용 표현과 결합**:
        * **우측 결합**: 공용 표현 뒤에 붙은 표현이면서 `발동 시점/발동 조건/적용 대상`에 포함되는 표현은 전체를 독립 고유 속성으로 분류.
        * 예시) `신데렐라 : 크리스탈 웨이브`의 스킬1에서 `[사용 무기 변경 : 저격 모드]` -> `'저격 모드'`
        * **좌측 결합**: 공용 표현 앞에 붙은 표현이면서 `발동 시점/발동 조건/적용 대상`에 포함되는 표현은 전체를 독립 고유 속성으로 분류.
        * 예시) `은화 : 택티컬 업`의 `[카모플라쥬 : 1인 공격 대상에서 제외 직접 피격 시 해제]` -> `'카모플라쥬'`
        * 예시) `로산나`의 `[은신 : 1인 공격 대상에서 제외 직접 피격 시 해제]` -> `은신`
    6. **[효과] 내부의 독자적 기믹**
        * 스킬 `[효과]`로 분류되는 문구 안에 '기능 설명' 형태로 상세 실행 조건(예: 최대 대미지 누적량 도달 시, 공격 범위 내 분배 등)이 세부 기술되는 경우, 이는 단순 수치 버프가 아닌 독자적인 실행 라이프사이클을 갖춘 독립 기믹이므로 **`[고유 속성]`**으로 분류.
        * 예시) `트로니`의 `'누적 폭발 스킬'`은 기능 설명 내부에 자체 조건/적용 범위 규칙을 내포하고 있으므로 **트로니의 고유 속성**. (`누적 폭발 스킬 폭파 시 공격 범위 내 적들에게 분배 대미지`라는 `[효과]` 문구 자체가 발동 시점·적용 대상 성격을 담고 있어 규칙 1도 함께 충족)
    7. **복합 상태명(상위개념 : 하위개념)**
        * `[X : Y]` 형태의 대괄호(`[X : Y 삭제]`처럼 동작어 한 단어가 더 붙은 것 포함)에서 `X : Y`가 대괄호 바깥(헤더 등)에서 **글자 그대로 언급**되고 X, Y 둘 다 공용 표현이 아니면, `X : Y` 전체를 하나의 독립된 고유 속성으로 인정. 상위 카테고리(X) 아래 하위 변형(Y)을 구분하는 명명법이기 때문. 이때 대괄호는 콜론에서 쪼개지 않고(`명칭 X` + `효과 Y`로 나누지 않고) 통째로 효과 하나(`X : Y`, `X : Y 삭제`)로 남긴다.
        * 규칙 5와의 차이: 규칙 5는 한쪽이 공용 표현이라 그 반대쪽만 남기지만, 이 경우는 양쪽 다 이 니케만의 고유한 표현이라 전체를 분리하지 않고 하나의 이름으로 묶는다.
        * 헤더에서 언급되지 않는 `[이름 : 효과]`(예: `[딸기 사탕: 최대 장탄 수 56.7% ▲]`)는 평범한 명칭:효과 쌍이므로 이 규칙의 대상이 아니다. 이전 판에서 쓰던 "오른쪽에 숫자/%/▲/▼가 없으면"이라는 판정 대신 이 "헤더 언급" 조건을 쓴다.
        * 예시) `민트`/`프리카`의 `[무대 파트 : 보컬]`, `[무대 파트 : 댄스]` -> `'무대 파트 : 보컬'`, `'무대 파트 : 댄스'`(민트·프리카 둘 다 소유, 규칙 3의 "여러 니케가 가질 수 있음"에 해당). 민트의 `[무대 파트 : 보컬 삭제]`는 효과 `무대 파트 : 보컬 삭제` -> `[고유 속성] 삭제`가 된다.
        * 예시) `길티 : 마이티 바니`/`신 : 스위프트 바니`의 `[바니 모드 : 스탠스]`, `[바니 모드 : 인게이지]` -> `'바니 모드 : 스탠스'`, `'바니 모드 : 인게이지'`.
    8. **자원/상태 이름(헤더 틀 후보)**
        * `[이름 : 효과]` 표기 없이 효과 문구 속에만 나오는 자원/상태 이름(예: 메이든 : 아이스 로즈의 `MP 1 충전`, E.H.의 `폐품 10개 ▲`)도 고유 속성이다. 후보는 헤더에서 "자원/상태 이름이 오는 틀"로 찾는다 — `N 상태…`, `N 적용/발동/획득/포획/충전/사용 시·후·중`, `N 적용될/소환된…`, `N 개수가`/`N 수가`, `N이/가 <숫자 또는 최대/최소>…`(`자신의 MP가 0 이라면`, `배터리가 100% 도달 시`). 틀 바로 앞 1~4단어를 후보 창으로 잡고, 꼬리 수식어(`보유`, `제작`, `최대 중첩`…)와 숫자·단위를 뗀다. 문법 조각으로 끝나는 창(`적용`, `증가`, `효과` 등)은 버린다.
        * 후보는 어떤 니케의 `[효과]`로 분류되는 문구에서 **이름으로 쓰인 증거**가 있을 때만 그 니케의 고유 속성으로 인정한다(규칙 3: 효과 문구로 다루는 니케가 소유자). 증거 4형태 — (a) 효과/명칭 문구가 그 명사구로 시작하고 곧바로 수량·동작 단서(숫자, ▲▼, 수/개수/중첩, 충전·소환·포획·제작·소모·축적·삭제·해제·제거·발권·만큼, 또는 `이름 - 부제` 형태의 하이픈 구분)가 이어진다(`MP 1 충전`, `폐품 10개 ▲`, `유령 개수 6개 ▼`, `페르소나 - 요한나`), (b) `… X <명사구> 수 ▲`처럼 곱셈 표기 뒤에 단서와 함께 쓰인다(`X 용사 레벨 수 ▲`), (c) 효과 문구 전체가 그 명사구다(`[미래 예지]`, `[타겟 섬멸]`), (d) 명칭이 그 명사구와 같다. 더 긴 이름의 꼬리(델타 `인법 카모플라쥬` 속 `카모플라쥬`)는 증거가 아니다.
        * 한 틀에서 후보 창이 여럿이면 증거가 있는 **가장 긴 창 하나**만 본다. 그 창이 공용 표현이면 이 틀은 고유 속성이 아니다(더 짧은 창으로 내려가지 않음). `체력`, `스킬`, `버스트`처럼 어디서나 쓰는 일반 명사는 공용 표현 목록에 넣어 둔다.
        * 예시) `메이든 : 아이스 로즈` `MP`, `E.H.` `폐품`/`사제 탄창`, `솔린 : 프로스트 티켓` `티켓`, `일레그 : 붐 앤 쇼크` `유령`, `아크레인저 블랙` `배터리`, `아인` `니어 페더`, `네온 : 비전 아이` `화력 게이지`, `길로틴 : 윈터 슬레이어` `용사 레벨`, `그레이브` `미래 예지`, `D : 킬러 와이프` `타겟 섬멸`. `퀸(마코토)`/`유키코`/`아이기스` `페르소나`(각자 `[페르소나 - 요한나]`, `[페르소나 - 코노하나사쿠야]`, `[페르소나 - 팔라디온]`을 부여하고 헤더의 `페르소나 상태 아군`에서 언급되므로 셋 다 소유).
    9. **수량 참조형 자원(헤더 언급 불필요)**
        * 헤더에서 한 번도 언급되지 않더라도, 한 니케만 쓰는 전용 자원 이름의 **수량이 다른 효과의 변수로 쓰이면** 고유 속성이다. 변수로 쓰인다는 것은 효과 문구가 `… X <명사구> (중첩) 수 ▲`처럼 곱셈 표기 뒤에 수량을 가져다 쓰거나(`공격력 13% X 소중한 추억 중첩 수 ▲`), `<명사구> 갯수만큼 …`처럼 수량만큼 동작한다는 뜻이다(`포획 사슬 갯수만큼 공격`). 이런 이름은 효과를 좌우하는 변수라 규칙 6(독자적 기믹)과 같은 취지로 인정한다(소유자는 규칙 3에 따라 그 문구를 쓰는 니케).
        * 단순히 `n개 충전`/`중첩량 n개 ▲▼`/`의 ○○ 소모`처럼 자기 수량이 늘고 줄기만 하는 자원은 고유 속성이 아니다(휘슬, 음소거, 탄환 주머니). 이런 이름은 아래 "전용 이름"이 된다.
        * 공통 오탐 방지 조건 — (1) 근거가 2개 이상일 것(서로 다른 효과 문구 2개 이상, 또는 같은 니케의 명칭 1개 + 효과 문구 1개 이상), (2) 그 명사구를 쓰는 니케가 정확히 한 명일 것(`최대 장탄 수`, `탄환 충전`, `해로운 효과 해제`처럼 여러 니케가 쓰는 말은 일반 용어), (3) 공용 표현·제어어 결합형·문법 조각으로 끝나는 말이 아닐 것.
        * 예시) `미하라 : 본딩 체인` `포획 사슬`, `아르카나 : 포츈 메이트` `소중한 추억`.
        * 한계 — 새 니케가 같은 명사를 쓰면 (2) 조건이 깨져 빠진다. 고유 속성 시트를 매번 새로 만들므로 시트를 보고 확인한다.
    * **공통 : 공백 무시** — "언급" 판정과 5단계 치환은 공백 유무를 무시한다. 같은 이름이 `메이드정신`(효과 쪽)/`메이드 정신`(헤더 쪽), `저격 모드`/`저격모드`, `1more`/`1 more`처럼 공백만 달리 쓰이는 경우가 실제로 있다. 같은 니케에서 공백만 다른 표기가 둘 다 후보가 되면 먼저 등록된 표기(이름 표기 `[이름 : 효과]`가 있으면 그쪽)를 대표로 쓴다.
* 고유 속성 제외 규칙
    1. **공용 표현 전치 구조의 미참조**
        * 공용 표현 앞에 특정 명사가 콜론으로 접두(결합)되어 있더라도, 그 명사가 `발동 시점/발동 조건/적용 대상`에 단 한 번도 참조되지 않는다면 고유 속성으로 인정하지 않음.
        * 예시) `나유타`의 `[부동심 : 불굴]`. `'불굴'`이 공용 표현이지만, `'부동심'`이 `발동 시점/발동 조건/적용 대상`에 참조되지 않으므로 고유 속성이 아님.
        * 예시) `치사토`의 `[사격 간파 : 무적]`. `'무적'`이 공용 표현이지만, `'사격 간파'`가 `발동 시점/발동 조건/적용 대상`에 참조되지 않으므로 고유 속성이 아님.
    2. **공용 표현과 시스템 제어어(면역/해제 등) 결합 규칙**
        * 기믹 명사 뒤에 '면역', '해제', '제거', '방해' 등의 시스템 제어 수식어가 붙는 경우, 비록 특정 니케가 유일하게 시전/참조하더라도 공용 표현(예: 기절)의 파생어에 해당하므로 고유 속성이 아닌 **`[공용 표현]`**으로 분류.
        * 예시) `D`의 스킬 설명에 등장하는 `'기절 면역'`은 공용 표현인 `'기절'`에 제어 수식어가 결합한 형태이므로 고유 속성이 아님.
    3. **조건부 미참조에 따른 고유 속성 배제**
        * 스킬 텍스트 중 `[효과]`로 분류되는 문구에서 콜론 결합형 기믹 명사를 스스로 시전하더라도, 본인 또는 타인의 스킬 텍스트 중 `발동 시점/발동 조건/적용 대상`에 해당하는 표현에서 그 명사를 단 한 번도 조건 대조나 참조용으로 소비하지 않는다면 고유 속성에서 철저히 제외.
        * 예시) `델타 : 닌자 시프`의 `[인법 카모플라쥬 : 1인 공격 대상에서 제외 직접 피격 시 해제]`에서 `인법 카모플라쥬`는 참조되지 않으므로 고유 속성이 아님.
        * 예시) `레이블`의 `[상상 실연 : 1인 공격 대상에서 제외 직접 피격 시 해제]`에서 `상상 실연`은 참조되지 않으므로 고유 속성이 아님.
        * 예시) `바이퍼`의 `[애교 : 1인 공격 대상에서 제외 직접 피격 시 해제]`에서 `애교`를 참조되지 않으므로 고유 속성이 아님.
        * 예시) `맥스웰 : 오디너리 미케닉`의 `과전류`는 참조되지 않으므로 고유 속성이 아님
        * 예시) `아이기스`의 `파피용 하트`는 참조되지 않으므로 고유 속성이 아님

## 본문 요소 판정 규칙
`■` 블록의 헤더 아래에 오는 본문 요소는 세 가지로 나뉜다.
* **효과** : 키워드가 될 요소. 예) `[최대 장탄 수 56.7% ▲]`
* **부가 옵션** : 키워드 대상이 아닌 요소. `n초 유지`(숫자와 `초` 사이 공백 허용), `n발 유지`, `n초 간격`, `n 중첩`, `지속`, `해제 불가`, `중첩 불가`, `중복 적용`/`중복 적용 불가`, `전투 중 (단) n회 발동`, `n회`, `n회 발동`, `최대 n%`, `최대 n 중첩`, `하위 효과 중복 적용`, `[해당되는 효과만 적용]`, `[단계별 효과만 적용]` 같은 고정 문구, 수량 상한·하한 표기(`최대 n회`, `최대 n개 보유`, `최소 n개 유지`, `최대 n레벨까지 성장`, `최대 n장까지 발권 가능`, `최대 MP n 축적`), 제거·삭제·해제 시점 표기(`마지막 탄환 공격 시 제거`, `풀버스트 진입 시 제거`, `변신 삭제 시 해제` — `시/후` 바로 뒤에 동작어만 오는 문구. 단 공용 표현 `1인 공격 대상에서 제외 직접 피격 시 해제`는 효과), `상태에 맞는 ○○만 적용`, 단순 해제/삭제/제거 표현(`디스트로이 해제`, `핀 포인트 해제`, `급소 공략 삭제`, `폐품 제거`, `중첩 제거`처럼 `<이름> 해제|삭제|제거`만 있고 수량이 없는 것 — 최종 목록에 넣지 않는다. 단 `버스트 스킬 사용 시 중첩 제거`처럼 앞에 헤더 문장이 붙어 있으면 헤더 문장(`버스트 스킬 사용 시`)은 서브 헤더로 떼어 발동 시점으로 남기고 `중첩 제거`만 버린다. `해로운 효과 해제 1개`, `탄환 100% 제거`처럼 수량이 붙은 것과 공용 표현은 효과), `재장전 n회 적용`, `풀 버스트 타임 동안 지속`, `부활 시 유지`, 그리고 **`~별 효과`/`~별 추가 효과`로 끝나는 패턴**(`[시작 횟수 별 효과]`, `[스쿼드 구성 별 효과]`, `[골든 칩 중첩량 별 효과]` 등 — 앞에 붙는 말이 니케마다 달라 고정 목록으로 못 잡으므로 끝맺음 패턴으로 판정)
* **명칭** : `[이름 : 효과]`의 콜론 왼쪽. 고유 속성 분석의 근거일 뿐 효과가 아님

아래 규칙들은 적용 순서가 있다. **규칙 3의 범위(명칭 단독 대괄호 스펙 시트) 안에 있는 줄은 그 범위 판정이 다른 모든 규칙보다 먼저 적용된다** — 블록 안에서는 라벨 형태가 무엇이든(순수 숫자 라벨, 이름+번호 라벨, 조건/대상형 라벨 등) `추가 효과`/`효과 N`/`효과 N 대상`이 아닌 한 전부 폐기한다. 범위 밖의 줄에는 1, 2, 4, 5, 6, 7번을 순서대로 적용하고, 그렇게 만들어진 효과 항목에는 8번(앞에 붙은 헤더 문장 분리)을 적용한다. 9번은 블록 단위 규칙이다.

1. **접두 라벨 제거** : `숫자 + (회|단계)(이하|이상)? + 콜론`(`1회 :`, `2단계 :`, `5단계이상 :` 등)으로 시작하면 라벨을 통째로 떼고 나머지 텍스트만 쓴다.
    - 라벨 뒤에 같은 줄 효과가 오면 그 텍스트가 그대로 효과가 된다(예: `1회 : [최대 장탄 수 45.17% ▲]` → `최대 장탄 수 45.17% ▲`). 니케마다 값만 다르므로 이후 숫자 치환·중복 제거가 정상 처리한다.
    - 라벨 뒤에 조건·대상이 오면 그 서브 헤더(독립 블록)의 텍스트가 된다(예: `2단계 : 기억 흡수 10 중첩 이상이라면` → `기억 흡수 10 중첩 이상이라면`).
2. **`효과N :` 서술 줄** : 라벨을 떼고 뒤따르는 내용을 본문 요소로 만든다. 뒤따르는 내용이 `<헤더 문장> [대괄호] [대괄호]…` 형태이면(`효과 4 : 적 사망 시 [폐품 2개 ▲] [최대 10개] [지속]`, `효과 1 : 동일 스쿼드 아군 전체에게 [크리티컬 대미지 23.51% ▲] [지속]`), 헤더 문장(경계 어미로 끝나는 시점/조건/선행 행동/대상 절)을 **서브 헤더(독립 블록)로 승격**하고 대괄호들은 그 블록의 본문 요소로 각각 분리한다. 같은 헤더 아래에서 효과마다 대상이 다른 경우가 실제로 있는데(그 헤더 자체에는 대상이 없을 때만 발생), 그 대상도 이렇게 서브 헤더가 되어 6단계에서 다른 헤더와 똑같이 슬롯으로 분해된다. 이 서브 헤더 블록은 상위 헤더의 슬롯을 상속하지 않는다(상속은 보류 상태 그대로). 뒤따르는 내용이 대괄호 없는 서술문이면 통째로 효과 하나로 둔다.
    - 이전 결정("효과 줄 앞 시점/대상은 분리하지 않고 전체를 효과로 둔다")을 폐기한 것이다. 디버깅 목록에 `[고유 속성] 대상에게 [최종 공격력 … 대미지] [...]`, `적 사망 시 [폐품 2개 ▲] [최대 10개] [지속]`처럼 시점·대상이 효과 키워드 안에 섞여 들어가는 문제가 확인돼 바꿨다.
3. **"명칭 단독 대괄호" 뒤 스펙 시트 폐기** : 먼저 "이름 단독 대괄호" 판정 — 대괄호로만 이루어진 줄은 (가) 줄 끝에 콜론이 붙어 있거나(`[구경났냐 짜식들아!!] :`, `[A.N. 모드] :`, `[화력 폭발] :`) (나) 뒤따르는 줄이 `기능 :`/`효과 :`/`효과 N :`/스펙 라벨로 시작하면(`[노출] [해제 불가]` 다음 줄 `효과 : [...]`) 첫 대괄호를 **이름(명칭)**으로 본다(나머지 대괄호는 부가 옵션/효과로 분류). 단 첫 대괄호가 수치 효과(`▲`/`▼`/`n%`)이거나 부가 옵션이면 이름이 아니다(`[공격 대미지 84.48% ▲] [10초 유지]` 바로 다음 줄이 이름 단독 대괄호 `[세븐스 드워프 풀 액티브]`인 경우 앞 줄은 효과). 이름이 정해지면 다음 규칙을 적용한다. `[사용 무기 변경]`, `[슈팅 스타]`처럼 콜론 없이 이름만 있는 대괄호 뒤에 `기능 :` 설명문과 스펙 라벨(`대미지`, `차지 시간`, `풀 차지 대미지`, `최대 장탄 수`, `공격 간격`, `공격 속도`, `펠릿 개수`, `유지 시간`, `발사체 부착/폭발 대미지`, `최초/일반 대미지`)이 이어지면, 그 블록에 속한 모든 줄을 폐기한다. 스펙 라벨과 값뿐 아니라 그 아래에 딸린 세부 표(예: 스펙 라벨을 다시 단계별로 쪼갠 `1단계이하 :`/`2단계 :` 같은 숫자 라벨 줄)도 전부 같은 블록으로 보고 함께 폐기한다 — 겉보기엔 "이름+번호 라벨"이나 "순수 숫자 라벨"처럼 보여도, 이미 폐기하기로 한 스펙 라벨의 세부값일 뿐이기 때문이다. 단, 같은 블록의 `추가 효과`(번호 있음/없음)·`효과 N`·`효과 N 대상`은 실제 게임 효과이므로 구제해서 라벨만 뗀다. 대괄호 안의 이름은 그대로 명칭 후보로 남는다. `추가 효과`가 콜론·내용 없이 단독으로만 등장하면(구분선 역할) 그냥 버린다.
    - 예) 맥스웰 : 오디너리 미케닉 버스트 `[사용 무기 변경 : 메티스 버스트 버스터] :` 블록 — `[차지 시간]`(단독 대괄호), `[과전류 단계별 효과]`(`~별 효과` 패턴), `[단계별 효과만 적용]`(부가 옵션), `차지 시간 : 3초`, `1단계이하 : 3초 고정` ~ `5단계이상 : 0.4초 고정`(차지 시간의 단계별 세부값), `대미지 :`, `풀 차지 대미지 :`, `최대 장탄 수 :`는 전부 폐기하고, `추가 효과 : [관통 특화]`만 구제해 효과 `관통 특화`로 남긴다.
    - 같은 블록의 `최대 [록 온] 대상 수 : 5개`, `최대 [오토 파이어 레디] 장전 수 : 5개`처럼 `최대 [이름] … : 수량` 형태의 줄도 스펙 라벨과 같은 수량 상한 줄이므로 폐기한다.
    - 대괄호로만 된 줄 바로 다음에 `라벨 : [효과]` 행들이 이어지면(예: D : 킬러 와이프의 `[명중 부위] [명중 시 적용되는 이로운 효과]` 다음 `파츠를 명중시킨 아군 : [...]`) 그 대괄호는 표 머리글(열 이름 설명)이므로, 부가 옵션/`이름 : 효과` 쌍이 아닌 평범한 대괄호는 버린다(숫자·`효과`·`추가 효과`·`기능`·`대상` 라벨 행은 표 행으로 보지 않는다).
    - 대괄호 하나짜리 `[<헤더 문장> 추가 효과]` 줄(예: `[자신에게 포메이션 AS 적용 중 추가 효과]`)은 뒤따르는 `효과 N :` 줄들이 적용되는 조건을 알리는 서브 헤더이므로 `추가 효과`를 떼고 헤더 문장을 서브 헤더(독립 블록)로 승격한다.
4. **이름+번호 라벨** : `생존본능 1`, `타겟 마킹 2`, `상태 1`처럼 이름 뒤에 번호가 붙으면 번호만 떼고 이름을 명칭 후보로 남긴다(규칙 3의 범위 밖에서만 적용). 숫자를 남기면 숫자 치환 단계가 단계 번호와 실제 수치를 구분하지 못해 서로 다른 단계별 효과가 하나로 뭉개진다.
5. **조건/대상형 라벨** : 내용 자체가 이미 조건·대상 문장이면(`100% 상태일 때 : [...]`, `자신에게 : [...]` 등) 일반 헤더·서브 헤더와 동일하게 취급한다. 구현 기준은 "콜론 앞이 경계 어미로 끝나고 콜론 뒤가 대괄호들뿐"이다. 단 **조건형 라벨**(라면/다면/경우/확률로/이면/으면/했다면/한하여로 끝나는 것 — 치사토 `70% 이상일 때 한하여 : [...]`, `100% 상태일 때 : [...]`처럼 상태 단계별 임계값을 알리는 라벨)은 쓸모없는 표현이라 **라벨만 버리고 뒤의 내용만 상위 블록에 남긴다**. 대상형/시점형 라벨(`명중 대상에게 : [...]`)만 서브 헤더로 승격한다. 서브 헤더 앞에 붙은 `대상 :` 라벨(`대상 : 명중 대상에게`)은 떼고 `명중 대상에게`만 헤더로 쓴다.
6. **`<Step n에서 사용 시 : 이름>` 분기** : 콜론 앞(`Step n에서 사용 시`)은 완전히 무시하고 어떤 슬롯에도 주입하지 않는다. 콜론 뒤 이름은 명칭 후보로 남긴다 — `[이름 : 효과]`의 명칭과 같은 위치이며 괄호가 `< >`일 뿐이다. 이 줄 아래 `■` 블록들은 시점 주입 없이 각자의 헤더 규칙대로만 처리한다.
7. **통째로 폐기하는 설명문(범위 밖 일반 규칙)** : 라벨이 `기능`, `특이사항`/`특이 사항`, `해제 조건`, `제거 시점`, `효과 N 대상`(부연설명이 붙은 것)이면 완전한 문장(자연어 설명)이므로 효과·조건·시점·대상 어디에도 넣지 않고 버린다. 명칭(대괄호 이름)이 있으면 그 명칭은 그대로 고유 속성 분석의 대상이다. 이 규칙은 규칙 3의 범위 판정과 무관하게 항상 적용된다 — `기능 :`은 이름 단독 대괄호 없이 헤더 바로 뒤에도 등장할 수 있기 때문이다(예: E.H. `■ 자신에게` 바로 다음 줄 `기능 : 폐품 획득 시 이로운 효과를 얻습니다.`, 벨벳도 동일). 규칙 3은 이 경우를 "이름 단독 대괄호가 선행하는 특수 상황"으로 확장해, 뒤따르는 스펙 라벨들까지 함께 폐기하는 역할을 한다.
8. **효과 문구 앞에 붙은 헤더 문장 분리** : 효과 항목이 `<헤더 문장> <남은 효과>` 형태이면(`효과 적용 후 사슬 감기 삭제`, `유지 시간 만료 후 아군 전체에게 충전량 회복`, `버스트 스킬 사용 시 중첩 제거`, `차지 속도 100% 초과 시 초과된 값을 차지 대미지로 변환`) 헤더 문장을 서브 헤더(독립 블록)로 승격하고 남은 효과만 효과 항목으로 둔다. 서브 헤더 블록에는 그 효과 바로 뒤에 딸린 부가 옵션(`[지속]` 등)만 붙고, 다음 효과/명칭부터는 원래 헤더로 돌아간다. 이 판정은 이름 표기와 상관없이 문구 자체의 모양만 보지만, 오탐을 막기 위해 다음 가드를 둔다 — (1) 헤더 문장이 2단어 이상일 것(`임시 개조 중첩 복사`의 '임시' 같은 단어 끝 글자 오인 방지), (2) 여러 문장(`. `)이 아닐 것(도로시의 낙인 서술문), (3) 남은 부분이 `제거/삭제/해제/초기화` 한 단어뿐이 아닐 것(그건 규칙 부가 옵션의 제거 시점 표기로 처리). `시`/`중`이 끝 글자인 일반 단어(`무시`, `임시`, `명중`)는 경계 어미로 보지 않는다("헤더 슬롯 분해" 절 참고).
9. **본문 요소가 없는 블록** : 서브 헤더만 있고 본문 요소가 하나도 없는 블록(예: 은화 : 택티컬 업의 `[자신에게 포메이션 LT 적용 중 추가 효과]`)도 헤더는 의미가 있으므로 `컨테이너` 행으로 남긴다. 고유 속성의 "언급" 판정(헤더 풀)과 헤더 슬롯 분해에서 이 헤더가 빠지지 않게 하기 위함이다.

## 토큰 키워드 제외
* `스킬 키워드 디버깅 목록`의 결과에서 `[고유 속성]`, `[스킬 1]`, `[스킬 2]`, `[버스트 스킬]`, `[특정 니케]`가 들어간 키워드와, 선행 행동으로 분류된 키워드를 제외한다. 그런 키워드는 대개 그 니케만 쓰기 때문이다.
* **전용 이름 제외** : 고유 속성은 아니지만 한 니케만 쓰는 이름이 든 키워드도 같은 방식으로 제외한다. 전용 이름은 4단계가 `전용 이름` 시트에 자동으로 만든다 — (1) 고유 속성이 되지 못한 이름(명칭) 전부(`인법 IFAK`, `소음 공해`, `오토 파이어 레디`, `맛의 여운`, `노출`, `격류` …), (2) 규칙 9의 조건은 충족했지만 수량 참조가 없어 고유 속성이 못 된 전용 자원 이름(`휘슬`, `음소거`, `탄환 주머니`). 키워드(공백을 뗀 형태)에 전용 이름이 들어 있으면 `제외 키워드` 시트에 사유 `전용 이름: ○○`로 남긴다. 이름을 `[고유 속성]`처럼 치환하지는 않는다(고유 속성이 아니고, 스킬명과 글자가 겹쳐 텍스트가 망가질 수 있다). 한계는 위 "알려진 한계"와 같다 — 예를 들어 델타가 `최대 누적량 ▲` 필터에서 빠진다. 2글자짜리 짧은 이름(`광기`, `근성`, `충심`)이 앞으로 일반 키워드와 글자가 겹치지 않는지 `제외 키워드` 시트에서 확인한다.
* 디버깅 목록은 제외 전 전체를 그대로 남긴다. 제외된 키워드는 사유(들어 있던 토큰 / 선행 행동)와 함께 `제외 키워드` 시트에 남겨서, 고유 속성 분석 오류로 범용 키워드가 잘못 제외됐는지 나중에 확인할 수 있게 한다.
* 알려진 한계
    - `시전자 기준 공격력 X [고유 속성] 수 ▲`처럼 범용 부분(공격력 ▲)이 함께 제외돼서, 해당 니케가 `공격력 ▲` 필터에서 빠질 수 있다.
    - 고유 속성이 아닌 니케 전용 이름이 든 키워드(예 : 델타 `인법 IFAK 최대 누적량 n% ▲`)는 제외되지 않고 마스터에 남는다.

## 효과 카테고리 배정
* 디버깅 목록의 효과 키워드 하나하나에 `공격류/공격보조류/방어생존류/체력회복류/유틸리티류` 중 하나를 배정한다(문장 분석이 아니라 키워드 단위 1회).
* 분류표(`{키워드 : 카테고리}`)는 공용 표현과 같은 성격의 입력이다 — 코드 안 사전이 원본이고 100% 수동 관리다. 효과 카테고리는 고유 속성처럼 규칙으로 기계 판정할 수 없어 공용 표현 쪽 성격에 가깝다고 판단했기 때문이다.
* 부트스트랩 절차
    1. 기존 마스터 시트에서 (키워드 → 카테고리) 쌍을 추출한다(엑셀 전체 재생성 전에 코드로 옮겨야 정보가 사라지지 않는다).
    2. 이를 시드로 위 카테고리 설명·예시를 기준으로 새 사전 초안을 만든다. 본문 요소 판정 규칙 등으로 키워드 문자열이 달라진 것은 재매칭하고, 매칭 안 되는 건 새로 판단한다.
    3. 애매하거나 눈에 띄는 것만 사람이 검수한다.
    4. 이후 분류표에 없는 새 키워드는 `미분류 효과`로 출력되고, 그때그때 사전에 추가한다. 미분류가 0건이 될 때까지 반복한다.

## 띄어쓰기 통일 규칙
* 정규식 규칙만 사용하고 사전은 두지 않는다. 크롤링 원문에서 표기가 갈리는 지점을 조사한 결과 다수/소수 형태가 명확히 갈리고(애매한 경우 없음), 비표준 공백 문자도 없었다.
* 적용 규칙
    - `][` → `] [` (닫는 대괄호 바로 뒤 여는 대괄호 사이 공백)
    - 숫자와 `중첩` 사이 공백 (`30중첩` → `30 중첩`)
    - `%`와 `▲`/`▼` 사이 공백 (`1.4%▲` → `1.4% ▲`)
    - 위 공백 규칙들은 전부 **같은 줄 안의 공백/탭**에만 적용한다. 줄바꿈까지 공백으로 취급하면 별도 줄이던 대괄호들이 한 줄로 합쳐져서, 줄 단위로 판정하는 구조 분해(이름 단독 대괄호/스펙 시트 판정)가 틀어진다(에이다 버스트의 `[특수 개조]`가 앞 효과 줄에 붙어 오분류되던 버그에서 확인).
    - `마다`는 앞말에 붙여 쓴다 (`2초 마다` → `2초마다`, `될 때 마다` → `될 때마다`, `10 중첩 마다` → `10 중첩마다`). 붙여 쓴 것과 띄어 쓴 것이 섞여 있으면 7단계 숫자 치환이 구조가 다른 두 그룹으로 보아 `…200발이 될 때마다`와 `…n발이 될 때 마다`가 중복 키워드로 남던 문제의 원인이었다.
    - `풀버스트` → `풀 버스트`(3건), `풀차지` → `풀 차지`(2건), `사용 했다면` → `사용했다면`(1건), `적들 에게` → `적들에게`(1건), `n% 만큼` → `n%만큼`(5건 대 4건 — 승환님 결정: 단위 뒤는 붙여 쓴다). 전부 숫자 치환 후에도 같은 키워드가 둘로 남던 띄어쓰기 중복의 원인이었다.
    - `n% 까지` → `n%까지`(2건 대 1건, `%만큼`과 같은 기준으로 단위 뒤는 붙임), `유지시간` → `유지 시간`(1건 대 효과 문구 다수)
    - `스킬2` → `스킬 2` (라피 : 레드 후드, 아르카나만 붙여 쓰고 나머지는 전부 띄어 씀)
    - 한글 글자와 `▲`/`▼` 사이 공백 (`티켓 수▲` → `티켓 수 ▲`)
    - 중첩 대괄호 평탄화 (`[최대 [록 온] 대상 수 10 ▲]` → `[최대 록 온 대상 수 10 ▲]` — 대괄호 파싱이 중첩을 다루지 못함)
    - 대괄호 바로 뒤에 붙는 부연 설명 괄호는 통째로 제거 (`[10초 유지] (동일 효과 중복 불가)` → `[10초 유지]`, 아래 `에게` 규칙과 같은 이유)
    - 말줄임표 `…` → `...` (길티의 `빌려 갈게에….`가 효과 쪽에는 `….`, 헤더 쪽에는 `....`로 갈려 같은 이름으로 인식되지 않던 문제)
    - `에게`/`들에게` 뒤에 괄호로 붙는 부연 설명은 공백 유무와 무관하게 통째로 제거 (`적 전체에게(파츠 포함)`/`적 전체에게 (파츠 포함)` → `적 전체에게`). 부연 설명이라 필터링에 불필요하고, 괄호 유무로 같은 대상이 다른 표현으로 갈리는 것을 막기 위함. 이 괄호 때문에 `~에게`로 안 끝나 보여서 서브 헤더 인식이 깨지는 부수 문제도 함께 해결됨(신데렐라 : 크리스탈 웨이브의 `자신이 저격 모드라면 적 전체에게 (파츠 포함)`에서 확인).
* 새 니케 추가로 지금까지 없던 오탈자 패턴이 발견되면, 그때 정규식 규칙을 추가하는 식으로 확장한다.
